# Context

## Definition

Context is the human meaning around a piece of work.

It is the situation the founder is trying to understand, continue, explain, or decide on.

A context is not the place where work appears. It is not a container, file, email, record, meeting, or model. Those things can contain evidence of a context, but they do not define it.

## What context contains

A context can contain:

- The customer, supplier, product, or internal responsibility involved.
- The problem being solved.
- The reason the work matters now.
- The current state of the work.
- The decision history.
- The unresolved questions.
- The people involved.
- The artifacts being used.
- The latest change.
- The point where work stopped.

The founder does not experience these as separate categories while working. The founder experiences them as one mental thread.

## Why context matters

The founder does not lose work because a container is missing.

The founder loses work because the mental thread connecting evidence, reasoning, decisions, and next state disappears during interruption.

When that thread is lost, the founder can still find artifacts. The hard part is remembering what they meant together.

## Context versus artifact

An artifact is something that can be found.

A context is what makes the artifact meaningful.

An email can show that a supplier asked a question. It does not explain the product issue, the customer pressure, the previous decision, the design concern, or the reason the answer matters.

A drawing can show a part. It does not explain the manufacturing problem, the supplier constraint, or the decision that changed the part.

A meeting can produce a decision. It does not automatically preserve the problem, options, objections, and consequences that made the decision necessary.

## Context versus task

A task describes an obligation.

A context describes the situation around work.

The founder can know the next task and still have lost the context required to do it well. The missing memory is not only "what should happen next." It is "what is this really about?"

## Context versus project

A project is a named container.

A context can cross project boundaries, split from a project, merge into another project, or continue after the project name has changed.

The founder needs to recover the context even when the project label is wrong, outdated, or too broad.

## Context as identity

A context has identity even when its visible labels change.

The same context can begin as a supplier question, become a product problem, touch a drawing, require a decision, create a meeting, and later become a reporting item.

The name changes. The underlying context remains.
