# Real Day

## Scope

This is a composite founder workday described through contexts.

The visible containers are messages, records, models, meetings, documents, calls, and memory. The actual work is the context that moves through them.

## Morning: several contexts are already alive

The founder starts the day with professional context already waiting.

There are supplier contexts, customer contexts, product contexts, production contexts, design contexts, reporting contexts, and unresolved decision contexts. They are not neatly separated. Several can appear inside the same message list, the same record system, the same design environment, or the same meeting agenda.

The first context loss happens immediately: the founder sees an artifact but must remember which context it belongs to, what came before it, why it matters, and whether a decision already exists.

## First switch: supplier question to product context

A supplier question triggers a product or production context.

The question is not the context. It is a doorway into the context.

The founder has to understand:

- Which product or part this affects.
- Which customer or internal need is behind it.
- Which business state matters.
- Which previous decision constrains the answer.
- Whether the issue is commercial, design, production, quality, or timing.

Context lost:

- The founder's interpretation of what the supplier is really asking.
- The urgency behind the question.
- The previous context interrupted by the question.
- The reason this issue matters now.

## Second switch: product context to artifact context

The product context leads to an artifact: a record, BOM, drawing, model, document, or previous conversation.

The artifact carries evidence, but not the whole context.

The founder has to remember why this artifact is being inspected, what question it is supposed to answer, and how it relates to the supplier, customer, product, decision, and reporting state.

Context lost:

- Why this artifact matters now.
- Which question it should answer.
- Which previous assumption is being tested.
- What decision depends on it.

## Third switch: artifact context to management context

While reasoning through an artifact, a management question arrives.

The founder now has to explain progress, status, or reasoning while the previous context is still mentally active. The interruption changes the work from solving the situation to explaining the situation.

The answer is not in one container. It requires the founder to reconstruct context across people, products, decisions, artifacts, blockers, and recent changes.

Context lost:

- Where the previous reasoning stopped.
- Which answer was forming.
- Which assumptions were active.
- Which details matter for the management answer.

## Meeting block

A meeting pulls the founder into another context.

The meeting may create new decisions, split an existing context, merge two contexts, or change the priority of a context that was already active.

The meeting itself is not the context. It is an event that changes context.

Context lost:

- Which paused context should resume first.
- Which meeting decision affects which context.
- Which details need to be reported later.
- Which work was actually completed before the meeting.

## Afternoon reconstruction

After the meeting, the founder reconstructs the day.

The reconstruction crosses artifacts and memory:

- Messages show communication traces.
- Records show business or operational state.
- Models and drawings show technical state.
- Documents show written artifacts.
- Meetings show events and decisions.
- Memory carries the relationships between them.

The missing object is the context itself: the active graph connecting the evidence.

## Reporting moment

The founder has to report what happened.

Reporting is not a timer problem. Reporting requires an explanation of contexts: what changed, why it mattered, what decision was made, what remains blocked, which artifact matters, and where work should resume.

The founder currently reconstructs the report manually by looking backward through traces and rebuilding the relationships between them.

## Where existing containers fail

- Messages store communication but not the whole context.
- Records store state but not the reason the founder entered them.
- Models and drawings store artifact state but not the supplier, customer, decision, or reporting context around them.
- Meetings create decisions but do not preserve the interrupted context.
- Timers record duration but not meaning.
- Task systems preserve obligations but not the context that made the work necessary.

## End of day

The founder ends the day with work completed across several unrelated contexts.

The hard question is not only "What remains open?" The hard question is "Which contexts changed, why did they matter, and where did each one stop?"

That is the product problem.
