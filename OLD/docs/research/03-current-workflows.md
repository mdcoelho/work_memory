# Current Workflows

## Evidence base

These workflows are extracted from repository documentation about the founder's current work behaviour.

## Context environment

The founder's work context is distributed across:

- Customers.
- Suppliers.
- Products.
- Problems.
- Decisions.
- Meetings.
- Business and operational records.
- Technical artifacts.
- Communication traces.
- Files.
- Documents.
- Task lists.
- Notes.
- Timers.
- Memory.

The repository previously named specific containers as if they were contexts. The corrected model treats them as evidence locations. The actual work is the context that crosses those containers.

## Workflow: reconstructing context

The founder reconstructs work by moving across scattered evidence:

1. Communication shows messages, questions, and coordination trails.
2. Records show business or operational state.
3. Technical artifacts show product or design state.
4. Calendar shows meetings and scheduled commitments.
5. Files and documents show artifacts touched during work.
6. Task lists show obligations and open loops.
7. Notes hold fragments of context.
8. Memory fills the gaps between all of them.

The workflow is slow because no single container explains the context, why it matters, how it changed, and where it should resume.

## Workflow: explaining progress

The founder explains progress by reconstructing context.

The pain is not simply planning the next action. The pain is explaining what was already done across interrupted contexts.

Progress reporting requires evidence of activity, decisions, blockers, changes, relationships, and reasoning.

Management questions force the founder to pause execution and reconstruct that evidence on demand.

## Workflow: resuming work

The founder resumes interrupted work by recovering context from memory and scattered containers.

The founder needs to know:

- What context was active.
- What changed.
- Why it mattered.
- What was decided.
- Which relationships matter.
- Where to continue.

Task lists do not provide enough of this context because they focus on future obligations.

Records and artifacts also do not provide enough context alone because each shows its own evidence without the full communication, supplier, customer, product, meeting, and decision context around it.

## Workflow: using task and project systems

The founder works near task and project management systems but rejects their process weight as the core shape of Work Memory.

Jira and ClickUp represent the wrong product direction: process administration, statuses, workflows, and team bureaucracy.

## Workflow: using notes and documents

The founder uses documents and notes as part of the reconstruction landscape.

Notes and documentation are not enough because they depend on either prior structure or later retrieval. Work Memory has to preserve context before it disappears.

## Workflow: using timers

The founder distinguishes duration from meaning.

Timers record elapsed time. Context memory records what the time meant. The founder values meaning over duration for remembering completed work.

## Workflow: using AI

The founder accepts AI only when it reduces cognitive load.

AI cannot interrupt capture, invent facts, require unnecessary review, or become the center of the product.

## Workflow breaks

- Work context lives across people, artifacts, records, communication, meetings, documents, and memory.
- Existing task systems show pending work better than context.
- Notes require too much organization or fail at retrieval.
- Timers record duration without meaning.
- Project management systems add process where the founder needs context.
- AI creates risk when it generates unsupported certainty.
